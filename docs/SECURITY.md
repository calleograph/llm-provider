# Безопасность — что реализовано

Этот документ описывает конкретные меры защиты, реализованные в проекте, и
где именно в коде их искать. Он не заменяет README (установка, эксплуатация),
а фиксирует состояние безопасности как есть — для аудита и для будущих правок.

## 1. Модель угроз для этого сервиса

Сервис принимает от аутентифицированного доменного пользователя текстовые
сообщения и файлы, обязательно обезличивает их через внутренний сервис и
только после этого передаёт обезличенный результат во внешний LLM API.
Административная часть отдельно аутентифицирует администраторов (локально
или доменной учёткой) и даёт им управлять доменными подключениями,
разрешёнными группами, подключёнными нейросетями, правами групп на
нейросети, параметрами сервиса обезличивания и лимитами токенов на
пользователя.

Ключевые классы угроз, которые здесь релевантны:

- LDAP injection через поле логина при входе в чат или в админку;
- утечка пароля пользователя (в логах, URL, JS-переменных, localStorage);
- обход TLS-проверки сертификата LDAPS (MITM на подключении к AD);
- обход обезличивания — отправка необезличенного текста или файла во
  внешний LLM API из-за ошибки в обработке отказа сервиса обезличивания;
- обход прав доступа — получение ответа от нейросети, недоступной группам
  пользователя, подменой идентификатора провайдера в запросе;
- утечка API-ключей внешних LLM и учётных данных сервисных доменных
  учётных записей;
- CSRF на формах чата и административных действиях;
- session fixation / кража сессии администратора или пользователя чата;
- перебор пароля (brute force) на входе в чат и на входе в админку;
- загрузка вредоносного или подменённого файла (двойное расширение,
  несоответствие содержимого заявленному формату, zip-бомба в OOXML);
- утечка исходного кода/секретов через веб-сервер (см. раздел 17);
- утечка содержимого чужого диалога одному пользователю чата от другого.

Ниже — что из этого закрыто и как.

## 2. LDAP injection

- Пользовательский ввод (`sAMAccountName`, CN группы), попадающий в LDAP-
  фильтр, экранируется через `escape_filter()` (ldap3 `escape_filter_chars`,
  та же семантика, что `ldap_escape(..., LDAP_ESCAPE_FILTER)` в 1.x)
  перед подстановкой — см. `llmp/ldap/client.py`
  (`find_user_dn_by_sam_account_name()`, `find_group_dn_by_cn()`,
  `is_member_of_group_recursive()`). Тест:
  [`tests/test_ldap.py`](../tests/test_ldap.py).
- DN группы (администраторов или разрешённой для чата), задаваемый
  администратором, используется только как **search base**
  (поиск с областью BASE по DN группы), а не как часть строки фильтра —
  синтаксически этот параметр LDAP API не подвержен filter injection.

## 3. Доменная авторизация

### 3.1. Вход в чат

`llmp/domain.py` (`ChatAuthenticator`):

1. LDAPS simple bind от имени самого пользователя (проверка пароля) — если
   для домена настроена read-only сервисная учётная запись, дальнейшие
   операции чтения каталога выполняются под ней, иначе — правами самого
   пользователя.
2. Поиск DN пользователя по `sAMAccountName`.
3. Проверка членства (прямого и через вложенные группы,
   `LDAP_MATCHING_RULE_IN_CHAIN`, OID 1.2.840.113556.1.4.1941) в каждой
   включённой разрешённой группе этого домена (раздел админки «Доступ к чату»).
4. Вход разрешается только при членстве хотя бы в одной разрешённой
   группе; итоговый набор групп пользователя сохраняется в сессию и
   используется `AccessPolicy` (раздел 5) при каждом запросе к нейросети.

Пароль пользователя используется только для LDAPS bind и нигде не
сохраняется. Строки Python неизменяемы, поэтому явного затирания памяти,
как в 1.x (`str_repeat("\0", ...)`), нет: пароль живёт только в памяти
текущего запроса и не попадает ни в БД, ни в сессию, ни в журналы.

### 3.2. Вход в админку

Локальный аварийный администратор (`llmp/auth.py`, `LocalAdminRepository`,
ровно одна запись в БД; новые пароли — argon2id, хеши `$2y$`/`$argon2id$`
из 1.x проверяются как есть, `llmp/passwords.py`) и доменная учётная запись,
входящая в настроенную группу администраторов (`DomainAdminAuthenticator`,
тот же LDAPS bind + проверка членства). Локальный администратор — только
аварийный доступ, не доменная учётная запись.

Если администратора ещё нет, `/admin/` ведёт на одноразовую форму
`/admin/setup.php`; после создания учётной записи форма закрывается.
Установщики создают администратора сами и печатают пароль один раз
(`python -m llmp.cli admin-reset --text`). Сброс пароля (консоль или
админка) завершает все открытые сессии администратора: в сессии хранится
отпечаток хеша пароля, и после смены он не совпадает.

## 4. TLS-проверка LDAPS

`Tls(validate=ssl.CERT_REQUIRED)` задаётся безусловно в
`llmp/ldap/client.py` (`LdapClient`), имя сервера сверяется с сертификатом,
доверие — только собственному CA bundle (`var/certs/ca-bundle.pem`),
собираемому из сертификатов, загруженных администратором в разделе
«LDAP-подключения» → «Сертификаты» (`llmp/certs.py`, `CaBundleBuilder`). Отсутствие
доверенной цепочки означает отказ LDAPS (fail-closed), а не понижение
уровня проверки. Для LDAPS системное хранилище CA ОС не используется и не
изменяется. Тест: [`tests/test_ldap_tls.py`](../tests/test_ldap_tls.py).

## 5. Права доступа к нейросетям

`llmp/llm/access.py` (`AccessPolicy`) + `llmp/llm/gateway.py` (`LlmGateway`):

- Право «доменная группа → нейросеть» хранится в таблице
  `llm_group_providers` и задаётся администратором в разделе
  «Доступ к чату»; индивидуальные права — `llm_user_providers`.
- Итоговый набор нейросетей пользователя — объединение прав всех его
  разрешённых групп, вычисляемое заново **на backend** при каждом запросе
  по данным БД на текущий момент. Отключение группы, домена или нейросети
  действует немедленно.
- `LlmGateway.complete_with_failover()` повторно проверяет право
  пользователя на каждую модель цепочки (включая резервные) перед
  обращением к внешнему API — подмена
  `provider_id` в запросе чата не даёт доступа к нейросети, не входящей в
  разрешённый набор.
- История диалогов и источники проектов читаются и изменяются только с
  фильтром по владельцу (`owner_key = sam@домен`) —
  `llmp/chat/conversations.py`, `llmp/chat/projects.py`. Один пользователь не может
  получить, переименовать или удалить диалог/проект другого пользователя,
  даже подставив чужой числовой id.

## 6. Обезличивание — fail closed

`llmp/anon/gateway.py` (`AnonymizationGateway`) — единственный компонент
приложения, обращающийся к внутреннему сервису обезличивания. Любой код,
отправляющий пользовательские данные во внешние сервисы (текст сообщения,
извлечённый текст файла, инструкции и источники проекта), обязан сначала
получить обезличенный результат отсюда; `LlmGateway` принимает только
объект `AnonymizedText` (`llmp/anon/text.py`), а не произвольную строку —
обычная строка отклоняется проверкой `isinstance` до обращения к внешнему
API (код `empty_input`), необезличенный текст мимо этого шлюза не уходит.

Fail closed: при любой неопределённости — сервис обезличивания не
настроен, сетевая ошибка/таймаут, HTTP-статус не 2xx, некорректный JSON,
отсутствие ожидаемого поля результата, пустой результат для непустого
входа, нет подтверждения независимой проверки — выбрасывается исключение, и запрос во
внешний LLM API не отправляется. Пользователь видит понятное сообщение
без внутренних технических деталей.

В диагностический журнал пишутся только метаданные (длины текста, число
фрагментов, длительность, HTTP-статус, код ошибки) — ни исходный текст, ни
ответ сервиса обезличивания не журналируются.

Сервис один — встроенный `anonymizer` (см.
[ANONYMIZATION.md](ANONYMIZATION.md)): контейнер во внутренней сети без
выхода в интернет, адрес и токен — из окружения (`ANONYMIZER_URL`,
`INTERNAL_API_TOKEN`), в БД и в админке их нет. Сообщение и вложения
обезличиваются одним вызовом, результат проверяется независимо. Внешних
сервисов обезличивания нет: пользовательские данные до обезличивания не
покидают сервер. Сохранённые настройки удалённых в 2.0.0 режимов (DocClean,
произвольный JSON API) не читаются.

## 7. Обработка файлов

`llmp/files/processor.py` (`FileProcessor`) + `llmp/files/extractors.py`:

- Расширение файла должно входить в список поддерживаемых
  (`FileProcessor.supported_extensions()`); заявленное расширение
  проверяется по сигнатуре первых байт файла (`matches_signature()` у
  каждого экстрактора) — двойное расширение или подмена типа файла
  отклоняются до попытки разбора содержимого.
- ZIP-контейнеры (DOCX/XLSX/ODT) разбираются с лимитами на число записей
  архива, размер записи и суммарный распакованный размер (`ZipPackage` в
  `llmp/files/extractors.py`) — защита от zip-бомбы; XML разбирается через
  `defusedxml` (без внешних сущностей).
- Внешние программы (`pdftotext`, `pdftoppm`, `tesseract`) запускаются
  через `subprocess` без оболочки, с тайм-аутом; они входят в образ `app`,
  пути зафиксированы (`/usr/bin`) и в админке не редактируются. На изображения внутри DOCX/ODT действует тот же
  лимит OCR, что и на страницы сканов.
- Загруженный файл сохраняется во временный файл вне document root
  (`var/tmp/...`) и удаляется сразу после извлечения текста, независимо от
  результата обработки. Сам файл во внешний LLM API не передаётся —
  передаётся только обезличенный извлечённый текст.
- Если исходный файл не удаётся надёжно обработать и обезличить (например,
  скан без текстового слоя при недоступном OCR), запрос блокируется, а не
  отправляется частично — тот же принцип fail closed, что и для текста.

## 8. Хранение и передача паролей

Пароли принимаются только через `POST`-тело, никогда через
`GET`/URL/query string, и не сохраняются нигде, кроме хеша пароля
локального администратора.

## 9. CSRF

Synchronizer token pattern (`llmp/security.py`: `csrf_token()`, `csrf_verify()`),
привязан к сессии, проверяется на каждом изменяющем состояние POST-запросе
как в админке, так и в API чата (`X-CSRF-Token` или поле `csrf`).

## 10. Сессии

`llmp/security.py` (`SessionStore`) — общий механизм для админки и чата.
Сессии хранятся на сервере, в таблице `web_sessions` SQLite; в браузере —
только случайный идентификатор в cookie `ADPWD_SESSION` (HttpOnly,
SameSite=Strict). Флаг `Secure` ставится, когда запрос пришёл по HTTPS или
с заголовком `X-Forwarded-Proto: https`; поэтому доступ по
`http://IP:порт` работает, а за HTTPS-прокси cookie защищена. Подделка
заголовка по http лишь заставит браузер не вернуть cookie — вреда нет.
При входе идентификатор сессии меняется (защита от session fixation).

Сессия администратора (`AdminSession`, `llmp/auth.py`) и сессия
пользователя чата (`llmp/chat/core.py`) используют разные ключи одной
сессии и не пересекаются: выход из чата не завершает сессию
администратора и наоборот. Таймаут бездействия администратора
настраивается в «Настройки» (5–1440 минут, по умолчанию 4 часа, не больше
24 часов); сессия чата — 4 часа бездействия и 12 часов абсолютное время
жизни. Истёкшие сессии удаляет планировщик раз в час. Сессии версии 1.x
не переносятся: после обновления с неё все входят заново один раз.

## 11. Rate limiting

`llmp/security.py` (`RateLimiter`, таблица `rate_limit`), окно 15 минут, экспоненциальная
задержка после 5 попыток (не вечная блокировка). Применяется к входу в
чат и к входу в админку по отдельным ключам (IP + назначение).

## 12. Секреты

`llmp/secretbox.py` — AEAD-шифрование (AES-256-GCM, формат
`base64(iv12‖tag16‖ct)`, тот же, что в 1.x: значения, зашифрованные
версией 1.x, читаются как есть). Мастер-ключ — в переменной окружения
`APP_MASTER_KEY` (`.env`, права 600) или в `var/data/master.key`
(права 0600). На установленной системе без ключа — явная ошибка, а не
создание нового. Используется для:

- API-ключей внешних LLM-провайдеров и дополнительных HTTP-заголовков
  (`llm_providers`);
- пароля read-only сервисной учётной записи домена, если она задана
  (`ldap_configs.service_password_encrypted`);
- токена/пароля сервиса обезличивания и пароля SMTP (`app_settings`).

При смене адреса LDAP-сервера или провайдера LLM сохранённый пароль
сервисной учётной записи или ключ API стирается — секрет не уйдёт на новый
адрес без повторного ввода.

После сохранения секрет в интерфейсе не показывается целиком — только
последние символы ключа (для опознания) либо факт, что значение сохранено.

## 13. Общие HTTP-заголовки

`Content-Security-Policy` (`default-src 'self'`, без
`unsafe-inline`), `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`,
`Referrer-Policy: no-referrer`, `Cache-Control: no-store` — см.
`SECURITY_HEADERS` в `llmp/web/core.py` (добавляются к каждому ответу).

## 14. Исходящие HTTP-запросы приложения

`llmp/http.py` (`HttpxTransport`, httpx) — единый транспорт для обращений к
сервису обезличивания и к внешним LLM API: проверка TLS-сертификата и
имени хоста всегда включена, редиректы не выполняются, переменные
окружения прокси не учитываются, разрешён только `https://` (кроме
встроенного сервиса обезличивания во внутренней сети), размер ответа ограничен. Доверие —
системное хранилище сертификатов ОС; если в блок «Сертификаты» загружен
корпоративный CA, используется собранный из него bundle. Ошибка TLS
называется явно (вид `tls`), а не «сервис недоступен».

## 15. Журналы

Расширяют существующий механизм, не заменяют его. Раздельные журналы:

| Журнал | Назначение |
| --- | --- |
| `app_log` | операции пользователей чата (вход/выход, обращения к нейросетям, обезличивание, работа с файлами) |
| `audit_log` | административные действия (изменение доменов, групп, нейросетей, прав, лимитов, настроек обезличивания) |
| `diagnostic_log` | техническая диагностика LDAPS/TLS/обезличивания/LLM-шлюза, без содержимого запросов |

Пароли, API-ключи, LDAP-пароли и содержимое пользовательских
запросов/файлов в журналы не записываются ни в одном из трёх журналов.

**Аудит и DLP (телеметрия)** (`llm_outbound`, `llmp/chat/telemetry.py`, `llmp/chat/dlp.py`) — отдельный журнал того, что ушло во внешние
нейросети: пользователь, модель (и резервная, если ответила она), тип запроса (сообщение, сводка, состояние
проекта), вложения, токены, длительность, результат и **текст сообщения ровно в том виде, в каком он ушёл**
(обезличенный; при «не обезличивать» — как отправлен, с флагом `unanonymized`). Текст хранится сжатым, без
внешних ключей — удаление диалога пользователем записи не удаляет. Срок хранения — «Аудит и DLP → Правила и
хранение» (по умолчанию 365 дней, 0 — бессрочно), зачистка раз в час планировщиком порциями вместе с поисковым
индексом и срабатываниями. Сбой записи телеметрии не мешает отправке (причина — в `diagnostic_log`, источник
`telemetry`). Под полем ввода чата пользователь видит подписи «Обезличивание включено» и «Учёт запросов включен»
с пояснениями.

При записи текст попадает в полнотекстовый индекс `llm_outbound_fts` (FTS5 без копии текста) и проверяется
правилами DLP (`dlp_rules`: встроенные шаблоны — пароли и ключи, карты с проверкой Луна, паспорт, СНИЛС и ИНН с
контрольной суммой, грифы, контакты, внутренние адреса, финансы, сделки — и правила администратора: слова по началу
или регулярные выражения). Совпадения — в `llm_outbound_dlp`, наибольшая важность — `llm_outbound.dlp_severity`;
администратор отмечает записи «Норма» или «Инцидент» (`review`, кто и когда). После правки правила его прежние
срабатывания снимаются сразу, а журнал за 7 дней перепроверяет планировщик.

Каждый просмотр администратором страницы ленты, карточки записи, списка диалогов и переписки пользователя, каждая
выгрузка CSV, отметка записей и правка правил пишутся в `audit_log` (`telemetry_feed_view`, `telemetry_record_view`,
`telemetry_user_view`, `telemetry_conversation_view`, `telemetry_export`, `telemetry_review`, `dlp_rule_create`,
`dlp_rule_update`, `dlp_rule_enable`, `dlp_rule_disable`, `dlp_rule_delete`, `dlp_rescan`); выгрузка — только с CSRF-токеном, поля без CR/LF/табуляции,
ячейки, начинающиеся с `= + - @`, экранируются от выполнения формул.

## 16. Устойчивость к непредвиденным ошибкам

Непойманное исключение не показывает пользователю технические детали:
пользователь получает общий ответ 500, трассировка пишется в стандартный
поток ошибок процесса (`scripts/ctl.sh logs app`), ожидаемые ошибки внешних сервисов — в
`diagnostic_log`.

## 17. Код и данные недоступны по HTTP

В 2.0 у веб-сервера нет «корня сайта» в каталоге проекта: nginx отдаёт
только статику `public/assets` и проксирует остальное в Uvicorn, а
приложение отвечает только своими маршрутами (`llmp/web/app.py`,
`llmp/web/routes.py`). Код, шаблоны, `var/` и SQLite не отдаются ни при
какой настройке nginx. `scripts/ctl.sh smoke` проверяет, что запрос к
файлу исходников возвращает 404. Прежние адреса (`index.php`, `api.php`,
`admin/index.php?section=…`, `admin/setup.php`, `healthz.php`) сохранены
как маршруты приложения, файлов `.php` нет. `healthz.php` отвечает только
с localhost или через доверенный прокси.

## 18. Изоляция истории между пользователями

`llmp/chat/conversations.py`, `llmp/chat/projects.py`: каждый метод чтения или изменения
диалога, сообщения, проекта или источника фильтрует по `owner_key`
текущего пользователя на уровне SQL-запроса, а не только на уровне UI.
Подстановка чужого числового идентификатора в API-запрос возвращает
`404 not_found`, а не чужие данные. См. регрессионные тесты в
[`tests/test_chat_repos.py`](../tests/test_chat_repos.py)
и [`tests/test_llm_access_policy.py`](../tests/test_llm_access_policy.py).

## 19. Экономичное и по умолчанию обезличенное хранение истории

Исходный (необезличенный) текст пользователя существует только в памяти
текущего запроса и никогда не записывается в БД или журналы — сохраняется
только результат, прошедший `AnonymizationGateway`. Длинные сообщения,
инструкции и источники проектов сжимаются (DEFLATE) перед сохранением в
SQLite — `llmp/compact.py` (формат 1.x: raw DEFLATE с префиксом `z`/`t`).
Сообщение, отправленное без обезличивания (`unanonymized = 1`), в
последующих ходах заменяется заглушкой: оно не уходит повторно ни в ту же,
ни в другую модель; ответ на такое сообщение помечается так же.

## 20. Лимиты токенов на пользователя

`llmp/chat/limits.py` (`UsageLimiter`): общий или индивидуальный лимит на день,
неделю или месяц (либо без лимита), расход хранится агрегатом
«пользователь × день» (`llm_usage`), а не записью на каждый запрос.
Превышение лимита или блокировка пользователя администратором проверяются
**до** обращения к сервису обезличивания и к внешнему LLM API — запрос не
уходит наружу, если лимит уже исчерпан. Перед обращением к LLM расход
резервируется, после ответа — пересчитывается по фактическим токенам, при
ошибке резерв возвращается (в 1.x возврат не работал). Сводки ранней
части диалога тоже учитываются в расходе.
