# Обезличивание

Режим один — **встроенный сервис** `anonymizer`: контейнер во внутренней сети без выхода в интернет. Внешних сервисов обезличивания
приложение не поддерживает (DocClean и произвольный JSON API удалены в 2.0.0; их сохранённые настройки не читаются). Адрес и токен
сервиса берутся из окружения (`ANONYMIZER_URL`, `INTERNAL_API_TOKEN`), а не из админки. Движок перенесён из «Переговорки» 0.76.1
(`backend/app/privacy/*`) без изменения логики.

## Путь данных

1. Приложение извлекает текст вложений локально (`llmp/files`, `FileProcessor`: TXT/CSV/MD, DOCX — с колонтитулами, сносками и примечаниями, ODT, XLSX, PDF — текстовый слой,
   сканы и изображения — OCR tesseract rus+eng). Изображение внутри DOCX/ODT, которое нельзя распознать, блокирует весь документ.
2. Текст сообщения и тексты всех вложений уходят **одним вызовом** `POST /v1/anonymize` — одна сессия замен: один человек получает одно обозначение
   в сообщении и во всех файлах (исправление «Переговорки» 0.56.1).
3. Движок: структурированные данные с контрольными суммами, секреты, словарь, NER (slovnet + navec) и морфология ФИО (pymorphy3), встроенная проверка
   `_verify`.
4. **Независимая проверка** (`app/verify.py`): результат заново прогоняется через детекторы почты, телефонов, IP, ИНН/СНИЛС/ОГРН/паспортов, карт и счетов
   и секретов. Найдено — один дополнительный проход той же сессией замен; осталось — HTTP 422, запрос в LLM не отправляется.
5. Любой сбой (модели не загружены, тайм-аут, ошибка движка, ответ не по контракту, пустой результат) — отказ; приложение отвечает пользователю 503 и ничего
   не отправляет наружу (fail closed). Исходный текст в БД и журналы не попадает; в журнал — объём, число замен, категории.

Пароли, токены и ключи скрываются **всегда**: при любом профиле и у пользователей с правом «отправить без обезличивания» (для них вызывается
маскирование только секретов — остальные категории остаются как есть).

## Профили и настройки

| Профиль | Люди | Организации | Места | Прочее |
|---|---|---|---|---|
| Базовый | «Иван И.» | с правовой формой и из словаря | остаются | метки и обозначения |
| Строгий | «Участник N» | все найденные | заменяются | метки |
| Настраиваемый | формат на выбор | область на выбор | действие на выбор | действие по каждой из 18 категорий |

Словарь организации (`термин;категория;замена`, узнаётся в любой форме слова), исключения, внутренние домены — в админке (**Система → Обезличивание**).
Там же: состояние сервиса и кнопка проверки, обработка файлов (размер файла, объём текста, OCR, его языки и лимит страниц, тайм-аут; доступность
`pdftotext`, `pdftoppm`, `tesseract` — они в образе `app`, пути зафиксированы) и «Проверка: что уйдёт в нейросеть» — текст или документ проходит тот же путь,
что сообщение в чате; исходные значения видит только администратор на экране.

## Согласованность обозначений

В пределах одного запроса — полная. Между сообщениями одного диалога согласованы имена в формате «Иван И.» (обозначение выводится из самого имени);
нумерованные обозначения (`[сервер 2]`, «Участник 3») между разными сообщениями могут различаться: таблица замен не хранится, иначе пришлось бы хранить
исходные значения.

## Сверка с эталонными наборами (методика «Переговорки»)

Скрипт `services/anonymizer/tests/benchmark_docclean.py` (наборы синтетические, в репозиторий не входят; путь к ним — аргумент). 16 текстов,
1140 значений «должно исчезнуть», 256 «должно остаться». Прогон 2026-11-15, тот же путь, что у запроса к сервису (с независимой проверкой):

| Профиль | Удалено обязательных | Лишние замены | Заблокировано проверкой | Скорость | Загрузка моделей | Пик памяти |
|---|---|---|---|---|---|---|
| Строгий | **98,7 %** | 22 из 256 | 0 из 16 | ≈ 13 500 знаков/с | 1,1 с | 229 МБ |
| Базовый | **98,1 %** | 16 из 256 | 0 из 16 | ≈ 13 500 знаков/с | 1,1 с | 229 МБ |

Цифры совпадают с результатом переноса в «Переговорке» (98,7 % / 98,1 %). До добавления повторного прохода независимая проверка блокировала
1 набор из 16 (пропущенный движком номер паспорта) — теперь он дозаменяется, а не уходит наружу.

Модели NER (≈ 29 МБ) загружаются один раз при старте контейнера; на запрос создаётся только лёгкий объект сессии замен. Параллельность —
`ANON_CONCURRENCY` (по умолчанию 4 одновременных обработки), тайм-аут — `ANON_TIMEOUT_S`.

## Скорость

Замер — `services/anonymizer/tests/timing_stages.py` (синтетические тексты, в выводе только числа; время этапов — по обёрткам функций движка,
медиана 7 прогонов) внутри образа: `docker run --rm -v "$PWD/tests:/srv/app/tests:ro" [--cpus 2] <образ> python -m tests.timing_stages`.
Хост 2026-11-15: QEMU, 20 vCPU **без AVX** (numpy работает на базовом наборе X86_V2), Python 3.12 в образе.

Время обработки движком, мс (`_process`: движок + независимая проверка; «вложение» — короткое сообщение + текст DOCX ≈ 5 900 знаков):

| Текст | до | до, `--cpus 2` | после | после, `--cpus 2` |
|---|---|---|---|---|
| короткий (81 знак) | 10 | 100 | 7 | 6 |
| средний (1 500) | 150 | 553 | 97 | 97 |
| длинный (20 000) | 2 029 | 5 522 | 1 394 | 1 391 |
| сообщение + DOCX | 821 | 1 586 | 414 | 412 |

Синтетические тексты повторяют слова, поэтому кэш морфологии в них выигрывает больше обычного; честнее — эталонные наборы
(`benchmark_docclean.py`, 97 662 знака, каждый текст новый): **9 800 → 13 500 знаков/с**, при `--cpus 2` **3 000 → 13 500 знаков/с**;
результат побайтно тот же (сверены хеши выходных текстов и замен на 38 парах «текст × профиль»).

Сквозная отправка в чате (`POST api.php?action=send`, локальный uvicorn + заглушка LLM по HTTPS, медиана), мс — всего / из них обезличивание
(по журналу шлюза):

| Сообщение | до | после | anonymizer `--cpus 2`: прежний образ → новый |
|---|---|---|---|
| короткое | 71 / 30 | 45 / 11 | 200 / 163 → 50 / 14 |
| среднее | 215 / 177 | 140 / 103 | 527 / 491 → 146 / 106 |
| длинное | 2 537 / 2 490 | 1 469 / 1 424 | 5 029 / 4 982 → 1 474 / 1 423 |
| короткое + DOCX | 938 / 896 | 471 / 429 | 1 897 / 1 858 → 451 / 412 |

Остальное (≈ 35–45 мс: права, контекст, запись в БД, вызов заглушки LLM по TLS) от размера почти не зависит.

Что было и что сделано:
- **Потоки OpenBLAS.** NER (slovnet) считает на numpy; OpenBLAS запускал потоки по числу ядер хоста (20), и при лимите CPU или
  параллельных запросах они мешали друг другу — в 3–4 раза медленнее. В образе `OPENBLAS_NUM_THREADS=1`, `OMP_NUM_THREADS=1`:
  на свободном хосте не медленнее, под лимитом — как на свободном.
- **Кэш разбора слов** (`names.models()`: `MorphAnalyzer.parse` в `lru_cache` на 20 000 слов, ≤ 80 МБ, результат — неизменяемый кортеж):
  разбор не зависит от контекста, а слова повторяются; до кэша морфология занимала ~30 % времени.
- **Повторная проверка движка** (`_verify`) искала секреты в уже чистом тексте дважды — теперь один поиск на версию текста.
  Независимая проверка (`app/verify.py`) не менялась.
- **Соединение приложения с сервисом.** Каждый вызов создавал новый httpx-клиент и TLS-контекст (≈ 11 мс, хотя адрес — http) и новое
  TCP-соединение. Теперь для внутренних http-адресов — один клиент с пулом keep-alive на процесс (`llmp/http.py`), таймауты прежние;
  сервис держит соединение 75 с (`--timeout-keep-alive`), клиент — до 60 с. Перезапуск контейнера пул переживает (закрытое соединение
  отбрасывается при следующем запросе).
- **Холодный старт** уже был правильным: модели (≈ 1,1–1,6 с) и пробная обработка — в фоне при старте, `/readyz` отвечает 200 только после
  них, запросы до этого — 503 (fail closed). Первый запрос после прогрева ≈ 13 мс, следующие ≈ 7 мс.

Интерфейс: сообщение появляется сразу; если ответ дольше 300 мс, строка под ним показывает этап — «Обезличивание…» →
«Отправлено в нейросеть…» → «Модель отвечает…» (после 5 с — секунды). Сервер отвечает одним JSON, поэтому этап оценивается по времени
(≈ 13 000 знаков/с + запас на вложения). Быстрые ответы ничего не мигают; строка есть с начала отправки — вёрстка не сдвигается;
при `prefers-reduced-motion` без анимации.

Что осталось (без изменения качества не ускорить): NER slovnet — ≈ 45 % времени (numpy без AVX); структурированные шаблоны — ≈ 20 %
(дважды: движок и независимая проверка; самый тяжёлый — `HEALTH`); обработка однопоточная из-за GIL — `ANON_CONCURRENCY` (4) даёт
очередь без простоя, а не ускорение одного запроса. Ориентир — ≈ 75 мкс на знак: 1 500 знаков ≈ 0,1 с, 20 000 ≈ 1,4 с.
